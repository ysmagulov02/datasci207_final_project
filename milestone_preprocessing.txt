Data preprocessing and intended user

The intended user is a commercial acquisition analyst in due diligence, with
property records, a walkthrough, seller/tenant operating estimates, and weather
for a stated reference year, but no utility history. This is not a listing-only
tool. Input availability is an assumption to verify with users; the field-level
audit lists possible sources and limitations. Equipment, occupancy, staffing,
and hours are optional/conditional information, not assumed public facts.

The 2018 CBECS source has 6,436 buildings. Excluding 79 inapplicable MFBTU targets
leaves 6,357 buildings. All 23 original predictors are retained, including
OCCUPYP. The fixed split is 4,449 training / 954 validation / 954 test (about
70/15/15, seed 42). No cross-validation or supervised feature elimination is used.
Model and engineering choices use the validation set; test is reserved.

Each of the 23 inputs gets a pre-fill missing indicator for the neural network
and other models. Numeric gaps use training medians; category gaps stay explicit.
EIA-supplied imputations are retained; NULL indicators do not recover values
EIA already filled. Weights and imputation-source flags remain metadata.

EIA replaces SQFT > 1,000,000 with regional averages and NWKER >= 5,000 with a
national average. We cap their model representations at 1,000,000 and 5,000 and
add separate threshold flags computed before clipping. Published values remain
in source_predictors.csv. Eligible counts: 125 large-area and 15 large-worker
records. NFLOOR 994/995 remains categorical; height over 50 has a bound and flag.

Eight proposed engineered features capture log size/staffing, workers per area,
area-hours, heated/cooled area, and area-weather exposure. Calculations use filled,
capped inputs; masked-building ratios are approximate. All 23 inputs and flags
are retained in the base (175 columns) and engineered (183 columns)
files. Scaling/encoding use training rows only. The delivered target remains
original MFBTU in thousands of Btu (kBtu).

A fixed-validation check compares base and engineered inputs using Ridge and
gradient boosting with fixed settings and a log fitting target. Metrics are in
documentation/feature_engineering_validation.csv. These are development results,
not final test scores or a full hyperparameter search. A neural-network comparison
is still needed. The brief EDA uses training buildings only and is unweighted.
